# System Audit — Health Collaboration OS

**Date:** 2026-09-28
**Scope:** entire repository
**Method:** all quality gates executed directly; full source review of `apps/api/src`; config, CI and documentation review; two parallel deep-dive reviews (structure integrity, application security). Findings marked ✅ were verified directly against the source.

---

## 1. Verdict

The system is **currently non-functional**: the workspace foundation (`packages/*`, `tooling/*`, `tests/`) has been reduced to `node_modules` only, so typecheck, lint, test, boundaries and build all fail (verified locally). CI fails at its own secret-scan step — a self-match inside the workflow file (B6) — so the gates behind it have never run in CI. The repository also had no version control until this audit.

Independently, the application code that does exist contains **one critical authorization gap** plus a cluster of high-severity defects in the consent/authorization layer that must be resolved before any HTTP route is wired up.

The design itself is sound — fail-closed PEP, fully parameterized SQL, no injection, no committed secrets, clean dependency audit. This is a recoverable project with serious defects, not a rotten one.

## 2. Blockers — the repository foundation is broken

### B1 · CRITICAL · Workspace packages contain only `node_modules` ✅

`packages/{auth,database,domain,permissions,ui,validation}` and `tooling/eslint-config` have **no `package.json`, no `src/`, no `tsconfig.json`** — only dependencies installed from an earlier healthy state.

Knock-on effects (each verified against the config that references it):

- `apps/*/tsconfig.json:2` extends `../../tooling/tsconfig/node.json` → **file does not exist** → typecheck _and_ build fail immediately.
- `vitest.config.ts:8-15` aliases all six `@health-os/*` packages to `packages/*/src/index.ts` → all missing → every test file fails to transform.
- `eslint.config.mjs:71-118` (domain/UI purity rules) and 10 of 13 `.dependency-cruiser.cjs` rules target `^packages/…` → **the boundary rules the frozen contract promises are unenforceable**.
- `apps/*/package.json` depend on `@health-os/*` via `workspace:*` → the imports are unresolvable at typecheck, lint, test and build time. (`pnpm install` itself still succeeds — see the B2 correction.)

### B2 · CRITICAL · `pnpm-lock.yaml` is malformed and out of sync ✅

Two YAML documents in one file (`---` at line 1 and line 158), declaring **13 importers** against **4 real projects** (`node_modules/.pnpm-workspace-state-v1.json` records `.`, `apps/api`, `apps/web`, `apps/worker`). `tooling/tsconfig` is declared as an importer for a directory that does not exist.

**Correction (after the first CI run, 2026-09-28):** the originally stated consequence — that `pnpm install --frozen-lockfile` _cannot succeed_ — was **wrong**. That step passes on a fresh checkout (observed in CI run 36422383803). The finding stands as a **lockfile-integrity defect**: stale importers and a two-document file that will break as soon as any dependency changes or a new project is added, but it is not what currently stops the pipeline.

### B3 · CRITICAL · `tests/` does not exist ✅

Referenced by `vitest.config.ts:58`, `package.json:23`, `eslint.config.mjs:120`, `tsconfig.eslint.json:29`, `README.md:65`, and the PHASE-0/2 audits. The architecture/freeze suite that guards the frozen contract has no files.

### B4 · HIGH · No version control until now ✅

`.gitignore` is correct but was inert — there was no `.git` at all. Consequences: no history, no diff, no rollback for whatever removed `packages/*/src`, no remote backup, and CI's `git ls-files`/`git grep` secret scan only functions after `actions/checkout`. The documentation itself acknowledged the gap (`docs/architecture/ARCHITECTURE-STATUS.md:39`).

### B5 · HIGH · Root `tsconfig.json` has an empty reference graph ✅

`"files": [], "references": []` — no composite graph exists, while `turbo.json:8-10` assumes `typecheck.dependsOn: ["^build"]`.

### B6 · HIGH · CI secret scan matches its own pattern definition ✅

`.github/workflows/ci.yml:68` runs

The scan greps the tree for an AWS secret-access-key identifier, a PEM private-key header, an OpenAI-style `sk-` token and an AWS access-key ID, excluding only `.env.example` and `pnpm-lock.yaml`:

```yaml
if git grep -nEI '<secret patterns>' -- ':!.env.example' ':!pnpm-lock.yaml' ; then
```

The pattern literal appears **inside that very line**, and the workflow file is not excluded — so `git grep` matches `.github/workflows/ci.yml:68` and the step exits 1. This is a pre-existing defect that only became visible on the repository's first push (the repo had no CI runs before 2026-09-28). It masks every later gate: `Format check`, `Lint`, `Typecheck`, `Tests`, `Boundaries`, `Build` and `Dependency audit` are all skipped in CI, so **CI has never actually observed them**.

**Fix:** add `':!.github/workflows/ci.yml'` to the exclusion list (applied in the same commit as this correction). Verified locally: with the exclusion the scan returns zero matches across the whole tree.

## 3. Security findings

**Operating context:** there is no HTTP layer (`apps/api/src/main.ts:26` → `httpListening: false`), no migrations and no RLS policy SQL anywhere in the repository. **Nothing is deployed and nothing is exploitable today.** These are pre-shipment defects — but they sit in the exact layer the product's own invariants claim is enforced.

### CRITICAL

#### C1 · Person can accept another person's access request → cross-subject consent materialization ✅

`apps/api/src/consent/service.ts:762-892`

```ts
actorPrincipalId = requirePersonActor(actor);        // :816 — only asserts actor IS a person
if (input.decision === 'accept') {
  ...
  await issueConsentInTx(client, {
    personId: row.person_id,                          // :834 — the REQUEST's person, not the actor's
    granteeProfessionalId: row.requester_professional_id, ... });
```

There is **no `row.person_id === actorPrincipalId` comparison anywhere** in the function, and the transaction runs under `runInSystemContext` (`:771`) so RLS is bypassed. If person A submits the UUID of a pending request targeting person B, active consent and compiled `access_grants` are created for (B → professional P), after which P's reads of B's health data succeed.

The ownership check would have to live in `domainAcceptAccessRequest`, imported from the **empty** `@health-os/domain` (`service.ts:10`) — therefore **it cannot be verified in this repository**. No test covers it (`consent.integration.test.ts:405-464` only resolves its own request).

**Fix:** explicit `row.person_id !== actor.personId → throw not_found` at `:816`, plus a regression test asserting _person B accepting person A's request → `not_found`, zero grants_.

### HIGH

#### H1 · Exported PEP-free raw-SQL primitive that hardcodes success ✅

`apps/api/src/authorization/authorize.ts:313-353` (exported via `authorization/index.ts:15`)

Accepts an **arbitrary caller-built `input.sql`**, sets the RLS principal context, runs it, and returns `allowedByRls: true` **unconditionally** — it never calls `authorizeHealthAccess`, the entire purpose of the class. Its doc comment ("_after policy ALLOW_") delegates the allow decision to the caller. No in-tree caller today; it becomes Critical the moment a route uses it.

**Fix:** delete it, or require an `AuthorizeHealthResult` and derive the flag from a real policy result.

#### H2 · `compileAndPersistGrants` mints active grants from a caller-supplied revision in system context ✅

`apps/api/src/authorization/compiler.ts:89-133` — takes a fully constructed `revision` object, no `ConsentActor`, no check that `revision.personId === input.personId`, no lookup of a persisted `consent_revisions` row. This violates the module's own stated invariant _"Person is sole consent authority"_ (`authorization/index.ts:5`). Currently uncalled (latent).

**Fix:** accept a `consentRevisionId` and load the revision inside the transaction.

### Verified controls (positive assurance)

- **No SQL injection** — every statement is parameterized (`$1…$n`); zero interpolated query templates outside tests.
- **No prototype pollution, no `eval`, no `new Function`, no `Math.random()` for tokens**; IDs use `crypto.randomUUID()`; no hardcoded credentials other than the cursor development key (M5).
- **Purpose is fail-closed before any DB work** (`authorize.ts:253-257`); no principal ⇒ deny rather than continue (`:258-279`).
- **Every decision re-reads live facts in one transaction** — relationship, membership, active consent (category + purpose + effective window), grants. **No caching anywhere**, so revocation is synchronous (`consent/service.ts:545-550`; latency tested at `authorization.integration.test.ts:290-309`).
- **Cross-person reads denied for person principals** (`summary.ts:27-29`, `clinical/types.ts:74-78`) and tested.
- **PEP-first on every clinical entry point** (17 call sites) with RLS as an independent second gate and `rowCount === 0 ⇒ throw`.
- **Private notes structurally excluded from the timeline** — explicit source list plus a hard guard that throws on leak (`timeline/project.ts:308-311`).
- **Cursor HMAC**: keyed, `timingSafeEqual`, bound to person _and_ filter shape, MAC over the exact base64url string (`cursor.ts:38,71,84-87`); tamper, cross-person and filter-mismatch cases all tested.
- **Invitations**: hashed at rest, single-use compare-and-set, TTL, recipient binding, row-locked (`invitations.ts:84-87, 358-367`).
- **Audit written in the same transaction as the decision** — failure ⇒ rollback ⇒ deny (`authorize.ts:185-220`), PHI-free metadata.
- **The web app cannot reach the database** (`apps/web/src/main.ts:14`).
- **No secrets in the repository**; `.env.example` holds commented placeholders only.

## 4. Trust and documentation integrity

The documentation currently **overstates** the system's state, which is itself a governance risk for a health-data product.

- `README.md:5-6` says _"Phase 0 … no health features yet"_ while `apps/api/src` holds 40 files / ~11k lines of clinical, consent, authorization, timeline and collaboration code. `package.json:6` and `.env.example:3` repeat the Phase 0 claim. The tree self-describes three phases: `web`/`worker` say 0, `apps/api/src/main.ts:13` says 3, the docs say 7.
- `ARCHITECTURE-STATUS.md:9` and `IMPLEMENTATION-PHASES.md:8-15` declare Phases 0–7 "DONE (audit PASS)", and `PHASE-7-AUDIT.md:8` reports _"35 files / 371 tests PASS"_ — this audit measured **0 tests executing**. The newest document in the same folder, `FOUNDATION-RECOVERY-REPORT.md` (2026-09-25), withdraws all of it: _"Phase 7 cannot be marked PASS"_, _"2 of 9 gates pass"_, _"DO NOT PROCEED TO PHASE 8"_. The status documents contradict each other.
- `docs/security/SECURITY-INVARIANTS.md:7-26` still asserts runtime **"P5 PASS / P6 PASS / P7 PASS"** for I-1…I-11 — states that cannot currently be verified.
- **PHASE-2…7 audits cite artifacts that do not exist**: migrations `0001–0020`, `packages/domain/src/timeline.ts`, `defaultTestDsn()`, `tests/architecture/*.test.ts` — 53 dangling `packages/*/src|migrations/…` references across `docs/`. (ADR-0001…0014 are all present and every index link resolves ✅.)
- **Environment drift:** `TIMELINE_CURSOR_SECRET` is read (`cursor.ts:19`) but absent from `.env.example`; 9 `HEALTH_OS_PG_*` CI variables are read by **no source file**; 11 documented variables (`NODE_ENV`, `API_PORT`, `API_CORS_ORIGINS`, …) are read by nothing — there is no dotenv loader anywhere.

## 5. Recovery reality — what is lost versus recoverable

| Artifact                                                    | Status                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript source for `packages/*`                          | ❌ **Lost** — source maps contain `sourcesContent` in 0 of 66 files; no prior `.git`, no backup copy, no editor history                                                                                                                                                                                              |
| **Compiled `dist/` for all six packages**                   | ✅ **Recoverable** — `.turbo/cache/*.tar.zst` holds `packages/{domain,auth,database,permissions,validation,ui}/dist/**` (13–23 archives each), including 7 archives with the Phase 7 `acceptAccessRequest` (`3584003c6b6ee334.tar.zst` → `packages/domain/dist/access-request.js:39`) plus full `.d.ts` declarations |
| SQL migrations `0001–0020` (including **all RLS policies**) | ❌ **Lost** — 0 `.sql` entries in any of the 762 cache archives; `migrate.js` is only a _runner_ that reads the missing directory                                                                                                                                                                                    |
| `tooling/tsconfig/node.json`, `tests/architecture/`         | ❌ **Lost** — not present in the cache; both are small and must be rewritten                                                                                                                                                                                                                                         |

**Implication:** restoring `dist/` plus minimal `package.json` shims would make `@health-os/*` resolvable again and could bring typecheck/build/tests back to green — but it would not restore the original source, and it would **not** restore the database schema or a single RLS policy. The controls the documentation claims (RLS defense-in-depth, `authz.can_read_health`) therefore have **no verifiable implementation on this machine**. Any recovered "PASS" without rebuilding them would be a false PASS.

## 6. Recommended order of work

1. **Version control first** — `git init` + initial commit + off-machine remote (this audit's push completes that step).
2. **Decide the recovery posture:** restore `packages/*/dist` from `.turbo/cache` as a _bridge_ to make gates executable, but treat `packages/*/src` and `packages/database/migrations` as **rewrite-from-scratch**, starting with the migrations/RLS layer — a claimed control with zero surviving evidence.
3. **Fix B1–B3** (package manifests, `tooling/tsconfig/node.json`, `tests/`) so typecheck, lint, test and build can run at all, then regenerate a valid single-document lockfile.
4. **Fix C1** (ownership check in `resolvePersonAccessRequest`) and **H1/H2** (delete or lock down the two system-context primitives) _before_ any HTTP layer exists.
5. **Reconcile documentation with reality** — a single truthful status document, and `SECURITY-INVARIANTS.md` downgraded from "PASS" to "UNVERIFIED" until each invariant has a passing test.
6. Re-run `pnpm verify`; only then consider phase claims.
