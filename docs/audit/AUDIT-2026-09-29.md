## 4. Security findings — status of prior audit

Operating context unchanged: no HTTP layer (`apps/api/src/main.ts:26` → `httpListening: false`), **no migrations, no RLS policy SQL anywhere** (0 `.sql` files in the tree). Nothing is deployed; these are pre-shipment defects in the layer the product claims is enforced.

### CRITICAL

#### C1 · ✅ FIXED 2026-10-02 (ownership check + regression test) · Person can accept another person's access request → cross-subject consent materialization ✅

`apps/api/src/consent/service.ts:762-892`

- `:816` — `actorPrincipalId = requirePersonActor(actor)` asserts only that the actor **is** a person.
- **There is still no `row.person_id !== actorPrincipalId` comparison anywhere in the function.**
- `:833-839` — `issueConsentInTx({ personId: row.person_id, ... })` materializes consent for the **request's** person, not the actor's.
- `:771` — the whole transaction runs under `runInSystemContext`, so RLS (which does not exist anyway) is bypassed.
- The intended guard is `domainAcceptAccessRequest({ request: base, personId: actorPrincipalId })` (`:818-822`), imported at `:10` from `@health-os/domain` — **a package with no source**. The check therefore **cannot exist, be verified, or even be executed** in this repository (`TS2307`).
- **No test covers it**: `consent.integration.test.ts:415` and `:436` resolve the caller's _own_ request; `:462` only proves a professional actor is rejected. No cross-person negative test exists.

**Fix:** explicit `if (row.person_id !== actorPrincipalId) throw new ConsentError('not_found', ...)` at `:816`, plus a regression test: _person B accepting person A's request → `not_found`, zero grants, zero consent rows_.

### HIGH

#### H1 · ✅ FIXED 2026-10-02 (primitive removed) · PEP-free raw-SQL primitive hardcoding success ✅

`apps/api/src/authorization/authorize.ts:313-353` (exported via `authorization/index.ts`)

`readHealthRowsAsPrincipal` accepts an arbitrary caller-built `input.sql`, sets RLS principal context, executes it, and returns `allowedByRls: true` **unconditionally** — it never calls `authorizeHealthAccess`. Doc comment delegates the allow decision to the caller. **No in-tree callers** (re-verified) — latent, Critical the moment a route uses it.

**Fix:** delete it, or require an `AuthorizeHealthResult` and derive the flag from a real policy result.

#### H2 · ✅ FIXED 2026-10-02 (load persisted revision + ownership assert) · `compileAndPersistGrants` mints grants from a caller-built revision ✅

`apps/api/src/authorization/compiler.ts:89-133` — takes a fully constructed `revision`, runs in `runInSystemContext` (`:97`), no `ConsentActor`, no check that `revision.personId === input.personId`, no lookup of a persisted `consent_revisions` row. Violates the module's own invariant "Person is sole consent authority". No in-tree callers (latent).

**Fix:** accept a `consentRevisionId`, load the revision inside the transaction, and assert `revision.personId === input.personId`.

## 5. Fresh sweep — new findings

### HIGH

#### N1 · CI has now failed three times without ever executing typecheck, tests, boundaries or build ✅

Run `36422985319` (after the B6 fix): **Install ✅ → Secret scan ✅ → Format check ✅ → Lint ❌**; `Typecheck`, `Tests`, `Boundaries`, `Build`, `Dependency audit` are all skipped. The repository's core gates have **never been observed by CI** in any run. The Lint failure is the same root cause as local: unresolved `@health-os/*` types (annotations cite `apps/api/src/authorization/authorize.ts:49,52,59`).

**Fix:** fix B1/B3 first — CI cannot go green until the workspace packages exist — then confirm every gate runs.

#### N2 · Every timeline read performs a full re-projection in system context ✅

`apps/api/src/timeline/query.ts:88-95` — with `sync !== false` (the default), each read calls `processTimelineOutbox(pool)` **and** `syncPersonTimeline(pool, personId)` under `runInSystemContext` before serving the page. `syncPersonTimeline` (`project.ts:331-353`) re-collects all canonical rows (8 source queries), diffs them, deletes orphans row-by-row and upserts every entry row-by-row.

- **Performance:** read latency is O(all canonical events for the person) plus N row-at-a-time writes, on every read.
- **Security:** read paths execute DDL-equivalent writes with RLS bypassed; failures are swallowed (`query.ts:92-101`), so a persistently failing sync silently degrades the projection while the API reports success.

**Fix:** move projection to the outbox drain (worker) and make the read path read-only; make sync opt-in/explicit.

### MEDIUM

#### N3 · CI workflow hardening gaps ✅

`.github/workflows/ci.yml`

- **No `permissions:` block** → the job runs with the repository default `GITHUB_TOKEN` scope instead of explicit least privilege (`permissions: { contents: read }`).
- **Actions pinned by mutable tag** — `actions/checkout@v4` (`:44`), `pnpm/action-setup@v4` (`:47`), `actions/setup-node@v4` (`:52`). Tag moves are a supply-chain vector; pin to commit SHAs.
- **Deprecation already firing:** GitHub annotates all three actions as "Node.js 20 … being forced to run on Node.js 24".
- Dev Postgres credentials are hardcoded in the workflow (`HEALTH_OS_PG_OWNER_PASSWORD: health_owner_dev_pw` etc., `:23-25`). They are ephemeral, CI-only, non-secret values — acceptable, but they must never be reused outside CI.
- Positive: no `continue-on-error`, no `if: always()` (README claim holds ✅), `timeout-minutes: 25`, concurrency cancel-in-progress, Postgres service with health checks, `set -euo pipefail` in the scan step.

#### N4 · Public repository with no branch protection and no dependency automation ✅

Repo `abhishek21lift-oss/health-collaboration-os` is **public**; `main` branch protection → **404 "Branch not protected"**; `.github/dependabot.yml` → **not found**; `dependabot_security_updates: disabled`.

Positive: `secret_scanning: enabled`, `push_protection: enabled` ✅.

**Fix:** enable branch protection (required checks + no direct pushes), add Dependabot (version + security updates).

#### N5 · System-context (RLS-bypass) usage outnumbers PEP usage ✅

29 `runInSystemContext(` call sites vs 25 `authorizeClinical(`/`authorizeHealthAccess(` call sites in `apps/api/src` (non-test). Several system-context uses are on **read/write paths for health data** (`consent/service.ts:771`, `timeline/query.ts:88-95`, `timeline/outbox.ts`, `timeline/project.ts`). The documented defense-in-depth (PEP **and** RLS) cannot hold when one gate is absent (no SQL) and the other is routinely bypassed — and the bypassing code contains C1.

#### N6 · Row-at-a-time write loops (N+1) in consent, grant compilation and projection ✅

- `authorization/compiler.ts:131-133` — one `INSERT … ON CONFLICT` per grant.
- `consent/service.ts:208-…` `upsertActiveGrants` — one statement per grant.
- `timeline/project.ts:321-347` — `rebuildPersonTimeline` `DELETE`s all of a person's entries then upserts one at a time; `rebuildAllTimelines` (`:355-370`) does this per person over a full `persons` scan.
- `timeline/outbox.ts:63-75` — one `UPDATE` per outbox row.

All inside single transactions → long-held locks and O(n) round trips as data grows.

**Fix:** batch with a single `unnest`-based upsert; move rebuild to an ops-only entry point with authorization.

#### N7 · Environment contract is fiction in both directions ✅

- **Exactly one `process.env` read exists in the entire codebase**: `timeline/cursor.ts:19` (`TIMELINE_CURSOR_SECRET`) — and it is the one variable **missing from `.env.example`**.
- CI exports 9 `HEALTH_OS_PG_*` variables — **read by no source and no test file**.
- `.env.example` documents `NODE_ENV`, `API_PORT`, `API_CORS_ORIGINS`, `DATABASE_URL`, `SESSION_SECRET`, … — **all read by nothing**; there is no dotenv loader.
- Integration tests obtain their DSN from `defaultTestDsn()`/`runMigrations()` imported from the **empty** `@health-os/database` package (`consent.integration.test.ts:7-14`), so even with a live Postgres they cannot run.

### LOW

- Test fixtures embed trivial passwords (`collaboration.integration.test.ts:125,159`) — acceptable for fixtures, but they will trip any future secret scan if the pattern broadens.
- `no-console` allows `warn`/`error` globally (`eslint.config.mjs:32`) and `apps/api/src/main.ts:35` logs a startup banner — harmless today (no PHI), worth a redaction rule before any health data exists (I-16).
